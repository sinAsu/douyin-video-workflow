# 长视频任务恢复与参数判断

## 状态与恢复

输出目录的 `.crop-state` 包含 `status.json`、`jobs.json`、每部 `.progress`/`.log`、后台 `worker.log` 和 `launcher.json`。读取状态后同时检查实际进程以及进度文件修改时间；PID 可能已被复用，需核对进程命令和开始时间。

`progress=end` 加退出成功，表示封装结束；`+faststart` 可能在编码到末尾后移动数 GB 数据，短时没有新进度不一定是停滞。判断时结合进程 CPU、磁盘活动、成品大小和最近日志，不能看到速度暂时为零就重启。锁仍被持有时不要启动另一份任务。

恢复使用同一 `run` 命令、输入目录和参数。已经验证的成品会重新核验后跳过；完整 `.partial.mp4` 会先核验再改名；不完整的残片保存在 `.crop-state/interrupted` 后仅重做这一部。普通 MP4 裁切编码不是下载续传，不承诺断点续编。

输入被改动、重命名、同名文件换内容，或参数改变时，脚本会拒绝复用旧输出。核实用户意图后选择新目录，不能删除身份记录强行覆盖。

## MP4 时长校验

容器 `duration`、各轨 `mdhd` 时长、`stts` 样本时间表和 `elst` 编辑列表意义不同。部分来源的 `mdhd` 有约 0.1～0.2 秒的陈旧差异，重新封装会修正它，不能仅据此宣告丢失音频。

脚本检查视频帧数和时长、音轨编码和样本数，并用 edit list 计算实际播放长度。当音轨原始头时长差异较大时，对各轨复制的压缩数据计算 SHA-256。头时长变化但数据一致、播放时长一致不应强迫重新编码。若有样本丢失、数据不一致或真实同步偏差，停止并排查，不加 `-shortest`、补静音、变速或简单放宽容差。

`checked()` 还解码每个输出开头、中间、结尾的代表帧；这是结构/帧数/音频核验加采样检查，不等于全片逐帧解码。用户需要进一步完整解码检查时另运行 FFmpeg null 输出，并如实说明耗时。

## 码率、质量和时间

`source-bitrate` 将视频平均码率目标设置为源视频样本总字节数×8/视频轨秒数，排除音频及 MP4 开销。VBR 输出不会严格等于目标；短片、复杂场景或编码器实现会有偏差。输出音频保持原样。若用户要求严格大小上限，不能承诺此模式满足，应另行讨论二次编码/目标预算。

`quality` 是近似视觉质量模式：QSV `global_quality=18`，NVENC `cq=19`，libx264 `crf=18`，AMF CQP。不同编码器的数值不等价；不要用数值相同推断质量相同。它可能比抖音已高度压缩的原片大很多，像素减少也不保证文件更小。

编码器选择按实际试编码是否成功，并不比较绝对速度或画质。用户有速度或体积优先要求时，用有代表性的 30～60 秒片段测速度、码率、画质；再以总时长/实测 speed 估算。不要把任务闲置时间计为编码耗时。长任务期间电脑需开机且不休眠，后台进程可以独立于聊天继续，但 Codex 自动监控仍依赖应用支持和电脑在线。
